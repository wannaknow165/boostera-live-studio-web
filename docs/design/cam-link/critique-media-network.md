# CRITIQUE: media-network

## VERDICT
Approve the transport, reject the plan as written.

P2P WebRTC with the gateway as a one-shot (non-trickle) HTTP relay is the right choice for one sender and one consumer. On a shared LAN it will connect even if the PC hides its addresses behind mDNS: the phone offers real host IPs, the PC's checks reach them, and the phone learns the PC as a peer-reflexive candidate. Sub-second delay is realistic (my estimate is 150-300 ms to the program canvas; nothing was measured).

v0 will still not survive its first test or its first hour on air, for seven reasons (details in the issues):
1. Nothing new is reachable today: the OLD copy is the one running, and the repo gateway rejects cross-origin POST, OPTIONS, bodies over 4 KB and unknown static files; `src=live` plays a file named "live".
2. The fallback has the wrong trigger, no way back to WebRTC and no sound.
3. The hub's race rules are undefined (program online, two tabs, lost offers, stale answers, no stop message).
4. The program page freezes her last frame for ever when the feed dies, and is fragile on every size or source change.
5. The launcher can silently run with none of its flags; two default-profile Chrome processes are running on this PC now.
6. The sender is configured to change resolution (`contentHint 'motion'`).
7. The Vardyverse embed, which is the stated requirement, has no reachable origin and dies on in-app navigation. It cannot be built in this step; build the capture page embed-ready and sequence the embed next.

What MUST be true for the first working test on today's bed:
- The repo copy runs as a second instance on its own ports. Do not replace the stack LIVE Studio is attached to.
- The phone's Wi-Fi is on the PC's LAN (192.168.1.0/24) with client isolation off. USB + adb reverse carries signalling only (TCP).
- The program window is started by the launcher with its own --user-data-dir, is in front, and its URL has opp=0.
- The gateway has the /api/live block: CORS for the program origin, OPTIONS, a 64 KB body reader.
- The offer is created after getUserMedia and sent from pc.localDescription.
- The PC has internet for the MediaPipe CDN.

What will probably fail there:
- Every WebRTC attempt if the phone is not on the LAN; it then drops to HLS (6-9 s behind, and silent as designed).
- Sound: blocked autoplay if the flags did not take effect, or a howl if the PC speakers are open.
- The first 5-10 s after each connect: soft picture that steps up in size.
- A frozen picture as soon as LIVE Studio covers a program window that was opened from the everyday Chrome.
- Signalling after an adb cable replug.
- Anything that involves Vardyverse or tickets.

### 3. [high] USB + adb reverse carries signalling only: without a shared IP network ICE cannot connect
**Problem:** adb reverse forwards TCP sockets. Media needs UDP between the two browsers, and ICE-TCP cannot rescue it: Chrome gathers only active TCP candidates, so neither browser listens. On a USB-only bed (phone Wi-Fi off, or on another network) every attempt spends 8 s and drops to HLS. A phone on mobile data against a PC behind a home router fails for most carrier NATs without a relay. 'Maybe on the same Wi-Fi' has to become a stated precondition with a recognisable failure, or the first test will be read as 'the WebRTC code is broken'.

**Evidence:** adb reverse/forward socket specs are tcp:, localabstract:, localreserved:, localfilesystem: (no UDP). PC probe: adapters up = Ethernet 192.168.1.x (default route, profile Private), Hyper-V Default Switch 172.30.176.x, WSL 172.28.80.x, VMware VMnet1/8; Wi-Fi adapter down; firewall on for all profiles. Chromium services/network/p2p/socket_manager.cc resolves '.local' names with HostResolverSource::MULTICAST_DNS only under `#if BUILDFLAG(ENABLE_MDNS)`, which Android builds lack, so the phone cannot rely on resolving the PC's mDNS candidate.

**Proposed change:** Precondition for test 1: the phone's Wi-Fi is on the PC's LAN (192.168.1.0/24), access-point client isolation off, any VPN on the PC off or set to allow LAN, 5 GHz preferred. Do not use USB tethering to create a path (it adds a default route through the phone on the broadcast PC). mDNS is not what blocks a LAN: the phone (camera granted) offers real host addresses, the PC sends checks to them and the phone learns the PC as a peer-reflexive candidate; keep the launcher flag anyway so the PC also advertises real addresses. Make the path visible: once per second read the nominated candidate-pair from getStats() and publish link.path {local:'host|srflx|prflx|relay', remote:'...', protocol:'udp|tcp', rttMs} in GET /api/live/status; on ICE timeout set link.lastError='ICE_NO_PATH' and show 'אין נתיב ישיר לשרת · בדקי שהטלפון על אותה רשת Wi‑Fi' before falling back.

### 4. [high] Fallback: wrong trigger, no way back, no sound, two deciders
**Problem:** (1) '503/504 -> fallback': PROGRAM_OFFLINE/TIMEOUT mean the only consumer of both transports is missing, so starting MediaRecorder and an ffmpeg transcode helps nobody. Since the design defines no return to WebRTC, a creator who taps while the program page is still loading (3-20 s after each reload) stays on the 6-9 s path for the whole live. (2) No upgrade path exists at all. (3) On HLS the audio is inside the muted engine <video>; item 2 plays audio only from the WebRTC track, so the fallback is a silent broadcast. (4) Two deciders: the phone decides to upload, the program separately 'checks overview for a running preview', which is the newest preview of any owner (the list has no owner field), so it can show a stale or foreign stream, and both transports can run at once. (5) Limits: an orphaned fallback stream lives 60 s (INPUT_TIMEOUT) and counts toward the limit of 2, so the third quick restart gets 409 BROADCAST_LIMIT; 60 s with the phone screen locked ends the stream and nothing restarts it; a 429 BACKPRESSURE is retried three times with no delay and then aborts the whole stream. (6) Cost of a downgrade: 8 s to detect plus about 6-10 s before the first HLS frame (1 s chunks, 1 s probe, 2 s segments, two-segment live sync), so 15-20 s of dead picture.

**Evidence:** Design item 3: 'If the offer returns 503/504 or the connection is not connected within 8 s -> fallback'; item 2: 'While no WebRTC link is connected, check /api/workspace/overview'. lib/mobile-broadcast.mjs:9 `Date.now()-s.lastChunkAt>60000)void this.stop(s.id,s.owner,'INPUT_TIMEOUT')`; :15 `filter(s=>active(s)||s.state==='stopping').length>=2)throw ...'BROADCAST_LIMIT'`; :11 view() has no owner; :41 `if(s.writing)throw ...('BACKPRESSURE'),{status:429}`; :18-19 '-analyzeduration','1000000' ... **Proposed change:** One decider (the phone); the program follows. Trigger: fall back only when an answer was applied and connectionState is not 'connected' 8 s later (ICE has no path). On 503 keep the preview, show 'מחכה למסך השידור בשרת…' and re-offer every 2 s; on 504 the same after two tries. Start: POST /api/workspace/broadcast/start {mode:'preview',mime}, then POST /api/live/capture/state {attemptId:null,transport:'hls',broadcastId}; the hub relays {type:'source',transport:'hls',broadcastId} on the program poll and the program plays exactly that id (the old 'newest preview' rule only with ?legacy=1). ### 5. [high] The long-poll hub is underspecified: four races as written, and no stop message
**Problem:** (a) 'Program online' is not defined. If it means 'a poll is parked', an offer that lands between two polls, or while the page is busy answering, gets a false 503; if it means 'seen in the last N seconds', a dead page costs every offer the full 8 s. (b) 'The most recent poller wins' with two open program tabs is a ping-pong: each tab's next poll evicts the other at request speed, and the window LIVE Studio captures can lose the link to a tab someone opened to have a look. (c) An offer is consumed on delivery: handed to a poll whose page is reloading, it is lost and the phone waits 8 s for nothing. (d) Stale answers: the program answers attempt A after the phone timed out or re-offered (auto-reconnect, a second tap and a visibility re-offer overlap); nothing rejects it and the program keeps a peer connection that never connects. Also missing: any message that tells the program to stop. capture/stop reaches only the hub, so the program shows the last frame until ICE gives up (about 5 s to 'disconnected', 15-30 s to 'failed').

**Evidence:** Design item 1: 'Waits up to 8 s for the program page to answer', 'one program page (the most recent poller wins)', 'a new offer from the same session replaces the old attempt'; the poll returns only '{attemptId, sdp, client} or 204'. The gateway has no long-poll today; fx/serve.mjs:25 notes `// res, not req: req 'close' fires right after a GET is read in Node 24`; mobile-gateway.mjs:136 shutdown has a 2 s hard exit.

**Proposed change:** Specify the hub as a state machine (lib/live-link.mjs, in memory, `now`/`timers` injected like createVardyIngest). Owner lease: the first poll with program=<pageId> owns the slot; the lease ends when its parked response has closed and no new poll came within 3 s. Another pageId during a live lease gets 409 {error:'PROGRAM_BUSY'} and stops polling, unless it sends takeover=1 (the launcher URL carries owner=1; ordinary tabs do not), in which case the old owner's parked poll is answered 409 {error:'PROGRAM_SUPERSEDED'} and that page closes its connection and stops. On pagehide the program sends navigator.sendBeacon(gw+'/api/live/program/bye?program='+pageId). online = a poll is parked OR the last poll ended under 3 s ago; the page's poll loop never awaits the answer flow. Poll replies carry seq and type: {seq,type:'offer',attemptId,sdp,client} | {seq,type:'stop',attemptId,reason} | {seq,type:'source',transport,broadcastId}. after=<seq> means 'handled up to here'; an offer stays deliverable until it is answered or 8 s old, so a reloaded page gets it again. attemptId is created by the phone (crypto.randomUUID()); the same attemptId posted again returns the stored result; a new attemptId from the same identity answers the previous parked POST with 409 {error:'REPLACED'}. POST program/answer returns 409 {error:'STALE_ATTEMPT'} unless the attempt is current and unanswered, and 410 {error:'CLIENT_GONE'} if the phone's request has closed (res.on('close') with !res.writableEnded); on either the program closes that connection at once. Program watchdog: not 'connected' 10 s after answering -> close. capture/stop and a replaced attempt both emit type:'stop'. close() answers every parked response.

### 7. [high] The program page never notices a dead, stalled or audio-only feed, and switching sources through #src is fragile
**Problem:** The engine has no listeners on its video and gates only on readyState < 2. When the link dies the last cut-out stays frozen over the live wall with no time limit. While readyState < 2 (every srcObject or hls swap) frame() is skipped but postFX() keeps painting on the uncleared canvas, so an effect in flight smears, re-zooms or darkens. Moving #src between a MediaStream and hls.js needs exact ordering each time. **Proposed change:** Never attach remote media to #src. ### 8. [high] contentHint 'motion' plus the default bitrate ramp make the sender change resolution at every connect and when the phone heats up
**Problem:** 'motion' selects the degradation mode maintain-framerate: when the encoder is CPU- or heat-limited, or bitrate is short, the sender lowers RESOLUTION. The sender also starts near 300 kbps and ramps up, so the first seconds after every connect arrive reduced and then step up. That is fine for a call; here every step changes the scale of the picture the body mask is computed from and (without the normaliser) resets the engine's buffers. An hour of camera + encoder + full-brightness screen makes thermal limiting on the phone the normal case.

**Evidence:** W3C mst-content-hint section 4.3: for a video track with the value 'motion', use 'maintain-framerate'; for 'detail', use 'maintain-resolution'. RTCDegradationPreference maintain-framerate: 'Degrade resolution in order to maintain framerate.' libwebrtc media/engine/webrtc_video_engine.cc GetDegradationPreference(): an explicit rtp parameter wins; content hint fluid -> MAINTAIN_FRAMERATE; detailed/text -> MAINTAIN_RESOLUTION; default MAINTAIN_FRAMERATE ('Keep MAINTAIN_FRAMERATE by default until BALANCED has been tuned'). fx/fx-engine.js:337-348 reallocates mask, plate and work canvases on any size change; :342 the mask input is half the incoming size.

**Proposed change:** live-capture.js: do not set contentHint 'motion'. After pc.addTransceiver(videoTrack,{direction:'sendonly',streams:[stream]}): `const p=sender.getParameters(); p.degradationPreference='maintain-resolution'; p.encodings[0].maxBitrate=3000000; p.encodings[0].maxFramerate=30; await sender.setParameters(p);` then read it back; if degradationPreference did not stick, set `videoTrack.contentHint='detail'` (same mapping). Before setRemoteDescription(answer), add `x-google-start-bitrate=2000;x-google-min-bitrate=800` to the fmtp of the negotiated video payload type (add an a=fmtp line for VP8 if there is none; ignored by non-Chromium senders). Create the connection with {iceServers, bundlePolicy:'max-bundle', rtcpMuxPolicy:'require'}. Every second send to the hub: frameWidth x frameHeight, framesPerSecond, qualityLimitationReason, target bitrate; when the reason is 'cpu' for more than 10 s the pill says 'האיכות ירדה: הטלפון חם או עמוס'. The normaliser on the program side absorbs whatever still changes.

### 9. [high] Reconnection is one sentence; five different failure cases need different reactions
**Problem:** 'Auto-reconnect with backoff (1, 2, 4, 8 s) when the link drops' does not say what a drop is. (1) Short Wi-Fi loss: connectionState turns 'disconnected' after about 3-5 s and usually heals alone; tearing down then costs more than waiting. 'failed' arrives only about 15-30 s after the loss, so waiting for it means half a minute of frozen picture. (2) Program page reloaded or crashed: the phone keeps sending into nothing until ICE times out, unless it is told. (3) Capture interrupted on the phone while the link is healthy: tab hidden, app switch, phone call, screen lock (Chrome for Android stops camera frames in background; iOS mutes or ends tracks), or the track ends because another app took the camera. Reconnecting does not help; the track must be re-acquired and swapped. (4) Signalling down, media fine: an adb cable replug removes the adb reverse mapping, a gateway restart loses in-memory sessions and hub state. P2P media is unaffected and must not be stopped by a failed status poll or a 401. (5) Phone IP changed (Wi-Fi to cellular): needs a new attempt. Unbounded retry loops over hours can also hit Chrome's cap of 500 RTCPeerConnections per process, on both pages. The 8 s 'connected' deadline is ambiguous: counted from the tap it is already spent by getUserMedia, gathering and the server's 8 s wait.

**Evidence:** Design item 3. Mozilla Bugzilla 1652884 / 1739163 describe muting camera tracks in background as Chrome-for-Android behaviour; WebKit bugs 204681 and 230698 (capture muted or ended in background). 500-connection cap: WebRTC bug 8571, Chromium bug 825576 (reports that closing does not free the slot promptly). lib/mobile-session.mjs:3 sessions live in memory; mobile-gateway.mjs:11 localRequest() is what adb reverse satisfies.

**Proposed change:** Phone states: idle -> acquiring -> offering -> connecting -> live -> (recovering | interrupted) -> live | fallback | stopped. recovering: enter on connectionState 'failed', or 'disconnected' for 4 s, or when hub status shows program.pageId changed or link.attemptId is no longer mine, or outbound bytesSent flat for 5 s. Action: keep the old connection, start a NEW attempt (new RTCPeerConnection, new attemptId), swap when it is connected, then close the old one. No ICE restart in v1. Retry delays 0, 1, 2, 4, 8, 15, 30 s (cap 30); after 10 failures in a row stop until 'online', visibility or a tap. Drop every reference to closed connections; expose pcCreated in stats; the program page reloads itself when idle and pcCreated > 200. interrupted: on track mute/ended and visibilitychange send POST /api/live/capture/state {attemptId, video:'live|muted|ended', audio:'live|muted|ended', visible}; the program shows the slate after 3 s (not a frozen face) and keeps audio; on return, if a track is ended or still muted after 1 s, call getUserMedia again and sender.replaceTrack() (no renegotiation), and re-request the wake lock. Signalling rule: a network error, 401 or 5xx on status/state never stops media; the pill says 'משדרת · אין קשר בקרה עם השרת'; the hub adopts state for an unknown attemptId when the owning program reports it (survives a gateway restart). Program states: idle -> answering -> connected -> stalled (no frames 1.5 s) -> lost (3 s, slate) -> idle; type:'stop' closes at once. The phone's 'connected' deadline is 8 s after setRemoteDescription(answer).

### 10. [medium] Non-trickle gathering will hit the 2 s cap on this PC every time, adding seconds to every connect and recovery
**Problem:** With the mDNS feature disabled (as the launcher does) Chrome enumerates every interface. This PC has Hyper-V and WSL adapters with no route to a STUN server; libwebrtc sends a binding request 9 times with a timeout that doubles from 250 ms to 8 s (about 40 s in total) before that port is done, so iceGatheringState cannot reach 'complete' before the cap. Expect 2 s on the program side plus up to 2 s on the phone in every negotiation and every recovery. Second trap: after the cap the code must send pc.localDescription.sdp (which contains the candidates gathered so far), not the string returned by createOffer/createAnswer (which contains none). The design also gives iceServers to the phone only; the program page needs the same list.

**Evidence:** PC probe: 'vEthernet (Default Switch)' 172.30.176.x and 'vEthernet (WSL (Hyper-V firewall))' 172.28.80.x are up next to Ethernet. libwebrtc p2p/base/stun_request.cc: `const int STUN_INITIAL_RTO = 250;` `const int STUN_MAX_RETRANSMISSIONS = 8; // Total sends: 9` `const int STUN_MAX_RTO = 8000;`. Design item 1: 'each side waits for iceGatheringState complete (or a 2 s cap)'.

**Proposed change:** Gather-done rule on both sides: resolve at the first of (a) iceGatheringState 'complete', (b) at least one host candidate seen and 300 ms without a new candidate, (c) 2000 ms; then send pc.localDescription.sdp. LAN default: GET /api/live/config returns {iceServers:[]} unless env LIVE_ICE_SERVERS (JSON) is set; host-only gathering finishes in tens of milliseconds. The program page reads the same config. bundlePolicy 'max-bundle' so only one transport gathers.

### 11. [medium] Codec and hardware encoding are left to chance and are invisible
**Problem:** Chrome on Android lists VP8 first and Chrome on Windows answers in the offerer's order, so the link will be VP8, encoded in software or by the chipset depending on the device. H.264 on Android exists only through the hardware encoder. An iPhone encodes H.264 in hardware and VP8 in software. Which encoder runs decides heat and battery over an hour, and nothing in the design chooses or records it. Forcing H.264 on Android now would swap a path already proven on this phone (VP8 through MediaRecorder) for device-specific hardware-encoder behaviour.

**Evidence:** public/mobile/render.js:76 mime order starts with 'video/webm;codecs=vp8,opus' (the path verified on the S21 FE today). MDN WebRTC codecs guide: iOS hardware H.264, software VP8. setCodecPreferences expresses what a peer wants to receive; if only the offerer sets it, it effectively decides both directions (platform-facts map, item 8).

**Proposed change:** v1: default negotiation. Add ?codec=h264|vp8|vp9 on the capture page: sort (do not filter) RTCRtpSender.getCapabilities('video').codecs so the chosen mimeType comes first and pass the list to transceiver.setCodecPreferences() before createOffer. Record on the phone: codec mimeType, encoderImplementation, powerEfficientEncoder, qualityLimitationDurations; on the program: decoderImplementation, powerEfficientDecoder; show them in /api/live/status. Decide after a 30-minute run per codec on the S21 FE: keep the one that holds 720x1280 at 30 fps with qualityLimitationDurations.cpu under 5 % of the time. iPhone later: it offers H.264 first by itself; if tracking misbehaves on rotated frames, remove the urn:3gpp:video-orientation extmap line from the answer so the phone rotates before encoding.

### 12. [medium] Audio: call-style processing, no lip-sync control, speaker echo, and a silent failure mode
**Problem:** (1) echoCancellation, noiseSuppression and autoGainControl all true is telephony processing: it gates music, singing and room sound, and echo cancellation has nothing to cancel because the phone plays no far-end audio. (2) Opus defaults to a low speech bitrate. (3) Audio and video are synchronised at the media elements, but the picture then passes rAF sampling, MediaPipe, the canvas and (with the normaliser) one more hop before LIVE Studio grabs it, while audio goes straight to the output device. My estimate is that sound will lead the picture by 60-150 ms (not measured); audio-early is the direction viewers notice first. (4) LIVE Studio records desktop audio, so the sound must be rendered on a Windows output device; if that is a loudspeaker in the creator's room, her phone hears it and the echo goes on air, not only at a desk test. (5) 'Retry on the first user gesture' has nobody to click in clean mode; without working launcher flags the LIVE is silent and only a log line says so.

**Evidence:** Design items 2 and 3. fx/index.html:45 `<video id="src" playsinline muted loop>`; fx/battle-stage.js:60 `v.muted = !this.sound;` (the program plays its own effect sounds on the same output). PC probe lists virtual render devices (for example 'NVIDIA Virtual Audio Device', 'Voice Changer Virtual Audio Device'). Effect of the constraints on Android capture mode was not tested on the device.

**Proposed change:** getUserMedia audio: {echoCancellation:false, noiseSuppression:false, autoGainControl:true, channelCount:1}; ?voice=1 restores the call profile for noisy rooms; try both on the S21 FE. Audio sender: encodings[0].maxBitrate = 96000. Program: play new MediaStream([audioTrack]) on a dedicated <audio>; add ?adelay=<ms> (default 0) as MediaStreamAudioSourceNode -> DelayNode -> destination, with the same stream also attached to a muted <audio> (Chrome needs an element sink for remote audio in WebAudio); choose the value from a clap test. Report audioEnergy (delta of totalAudioEnergy) and audioPlaying (!audio.paused && context running) in program/state; the pill says 'תמונה מגיעה · קול לא מושמע בשרת' when frames flow and audioPlaying is false. Launcher README: Windows default output = headphones or a virtual device, never open speakers; no microphone source in LIVE Studio.

### 13. [medium] On this PC the engine loop runs at the display rate (179-240 Hz) with no new-frame check
**Problem:** start() processes on every requestAnimationFrame. The displays here report 179 Hz and 240 Hz; the source is 30 fps. Face landmarks run on every tick and mask or pose on alternating ticks, all on the main thread, so the page works flat out re-analysing identical frames. That competes with LIVE Studio for the GPU and delays the fetch callbacks that answer offers.

**Evidence:** fx/fx-engine.js:1062 `const loop = () => { try { this.frame(performance.now()); this.postFX(); } catch (e) { this.log('frame error ' + e.message); } this.raf = requestAnimationFrame(loop); };` :410 comment 'Each model call blocks ~10 ms'. PC probe: 'NVIDIA GeForce RTX 4080 Laptop GPU | 5120x2160 @ 179Hz', 'Intel(R) UHD Graphics | 2560x1600 @ 240Hz'.

**Proposed change:** For src=live, in fx/index.html (no engine edit): after fx.start() call cancelAnimationFrame(fx.raf) and run `const loop=t=>{ blit(); if(t-last>=31){ last=t; try{ fx.frame(performance.now()); fx.postFX(); }catch(e){ logOnce(e.message); } } requestAnimationFrame(loop); }; requestAnimationFrame(loop);`. Report drawHz in program state. Later, put the same gate inside the shared engine.

### 14. [medium] The status pill can lie unless it is driven by the program's echo, and the echo is undefined
**Problem:** connectionState 'connected' plus rising bytesSent proves only that packets leave the phone. 'מחוברת · תמונה וקול מגיעים לשרת' is a claim about the server. Version 1.2.0 added outputConfirmed to stop exactly this kind of unproven label on the old path. The design names 'the program's state echo' but gives no fields, cadence or staleness rule.

**Evidence:** Design item 3. public/mobile/render.js:64 `const output=s.outputConfirmed?(...):'ממתין לאישור יציאת וידאו מהמקודד';`.

**Proposed change:** POST /api/live/program/state every 1000 ms while a connection exists (every 5 s when idle): {program:<pageId>, attemptId, state, showing:'webrtc|hls|slate', stats:{w,h,fps,framesDecoded,freezeCount,jitterMs,decoder,audioEnergy,audioPlaying,rafHz,drawHz,hidden,pcCreated}}. GET /api/live/status adds link.echoAgeMs. The phone polls status every 1000 ms (2000 ms on HLS). Pill rules: green 'מחוברת · תמונה וקול מגיעים לשרת' only when echoAgeMs < 3000, fps >= 15, audioEnergy rose and audioPlaying; otherwise 'מתחברת…', 'תמונה מגיעה · קול לא מושמע בשרת', 'מסך השידור בשרת מוסתר או ממוזער' (rafHz < 10), 'משדרת בחיבור איטי (כ־6 שניות עיכוב)' on HLS, or 'משדרת · אין קשר בקרה עם השרת' after three failed status calls.

### 15. [medium] Program polling starts only after MediaPipe has loaded from two CDNs
**Problem:** Source selection sits behind `await loadAll()` and `await fx.init()`. After every program reload the hub sees no program for 3-20 s (longer on a cold cache, and for ever if jsDelivr or storage.googleapis.com cannot be reached, because the engine module itself is a static CDN import). **Evidence:** fx/index.html:200-205 `await loadAll(); refreshRemix(); ... await fx.init(); fx.start(); ... if (qs.get('src') === 'phone') usePhone();`. fx/fx-engine.js:4 static import from https://cdn.jsdelivr.net/npm/@mediapipe/tasks-vision@0.10.14/vision_bundle.mjs.

### 16. [medium] On the bed the phone and the program page are the same identity, so 'loopback only' separates nothing
**Problem:** Through adb reverse the phone's requests arrive from 127.0.0.1 with Host localhost:<port>, so localRequest() is true and the phone is the 'local-desktop' session. It can call program/poll and program/answer; 'a different identity gets 409 BUSY' cannot be exercised; any desktop tab that opens /mobile/live replaces the phone's attempt; broadcast ownership is shared too. Any web page open in a local browser can also issue a GET to a loopback poll and swallow an offer.

**Evidence:** mobile-gateway.mjs:11 `export function localRequest(req,port){return[...].includes(req.socket.remoteAddress)&&!req.headers['cf-connecting-ip']&&!req.headers['x-forwarded-for']&&['127.0.0.1:'+port,'localhost:'+port].includes(req.headers.host);}` :25 `function auth(req){return localRequest(req,port)?localSession:sessions.get(cookies(req).wm_sid);}` :23 one shared localSession object.

**Proposed change:** Program routes: require the Origin header to be http://localhost:<upstreamPort> or http://127.0.0.1:<upstreamPort> in addition to localRequest() (a page cannot forge Origin; the capture page's origin is the gateway's own). ### 18. [medium] The raw camera track changes what viewers see: unmirrored, and landscape if the phone turns
**Problem:** Today's verified picture is the PWA's canvas: mirrored for the front camera and fixed at 720x1280. ### 19. [medium] Ticket key: the gateway does not have the stage token, and deriving the key from it ties capture to a viewing link
**Problem:** Outside my lens; I checked only the feasibility claim. The design says the server 'knows the plaintext token from its stage URL / env VARDY_STAGE_TOKEN'. Not found: no VARDY_STAGE_TOKEN or stage-token handling exists in the app, and the stage URL is a query parameter read in the browser on :8800 that never reaches the gateway process. **Evidence:** Search of the app for VARDY_ names finds only VARDY_INGEST, VARDY_BASE_URL, VARDY_SERVICE_KEY, VARDY_CREATOR_HANDLE (lib/vardy-ingest.mjs:6, lib/mobile-live-events.mjs:13). fx/index.html:99 `const stageUrl = stageUrlFor(location.search, location.hostname);` (browser only).

### 21. [low] TURN hook and production notes: credential code for a relay that does not exist, and the cheaper public-IP path is not stated
