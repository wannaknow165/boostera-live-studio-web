### 3. [blocker] Ticket key = SHA-256(stage token) is unsafe, and it is not 'nothing to copy by hand'
**Problem:** The stage token is a low-privilege wall-viewing secret that travels in URLs and is already exposed. Under v0 anyone who has seen it can mint a ticket and, because a new offer replaces the old attempt, put arbitrary picture and sound on her TikTok LIVE. Rotating the stage link (the creator's own 'צרי קישור' button) silently invalidates every ticket until someone re-copies the token to the server. The Node gateway never sees the stage URL, so a new value must be hand-copied anyway. Separately, a signed-in user can claim an unclaimed handle without proof and would then be issued tickets for that stage. Safe for a loopback-only test; a blocker before any public exposure.

**Evidence:** Stage token in URLs: APP/public/links.html:71 `'/clean/program?src=phone&stage=https://vardy-verse-connect.lovable.app/stage?creator=NAME%26t=TOKEN'`; it would also sit in the launcher's --app=<url> command line (readable by every local process) and in the phone's localStorage (LivePreviewPane.tsx `const LINK_KEY = "vardy-stage-link";`). The stage URL is a browser query parameter only: APP/fx/index.html:99 `const stageUrl = stageUrlFor(location.search, location.hostname);`. VARDY_STAGE_TOKEN: not found anywhere in APP (grep). From the Vardyverse map (not re-read by me): rotateStageLink is the only issuer and overwrites the hash; the token was printed in the Lovable chat; setManualHandle sets link_method 'manual' with no ownership proof.

**Proposed change:** HMAC key = the 32 bytes of sha256(VARDY_SERVICE_KEY), i.e. exactly service_keys.key_hash that Vardyverse already stores for ingest and that the gateway derives from an env name it already reads (APP/lib/vardy-ingest.mjs:6 `VARDY_INGEST=1 · VARDY_BASE_URL · VARDY_SERVICE_KEY · VARDY_CREATOR_HANDLE`). Ticket: `v1.<b64url{h,aud,kid,iat,exp,n}>.<b64url HMAC-SHA256(key,'v1.'+payload)>`, kid = first 8 hex characters of key_hash, exp at most 6 h ahead, refreshed when under 60 minutes remain. Gateway: compare lengths before timingSafeEqual; without VARDY_SERVICE_KEY every non-loopback /api/link/* request answers 503 {error:'LINK_DISABLED'}; a ticket authorises /api/link/* only, never a workspace session. The Vardyverse issuer refuses unless link_method==='tiktok_oauth' or an owner-approved flag is set. Delete the LIVE_TICKET_KEY override.

### 5. [high] Fallback rule is wrong: 'program offline' starts an HLS stream that nobody plays, with no way back to WebRTC
**Problem:** The program page is the only HLS consumer. When the offer returns 503/504 the program is absent or unresponsive, so starting MediaRecorder -> FFmpeg only burns phone battery and a libx264 transcode on the server while the phone shows some 'connected' state. On the HLS path her voice sits inside the muted engine video (a silent LIVE), the scan takes the newest preview of any device, and on iOS the existing mime order selects software VP8/WebM.

**Evidence:** Design section 3 ('503/504 or … not connected within 8 s -> fallback') and section 2 ('While no WebRTC link is connected, check /api/workspace/overview'). **Proposed change:** v1 has no automatic HLS. 503/504 -> state program_offline; poll GET /api/link/status every 3 s and re-offer when program.online is true. Timers: ICE gathering cap 2 s; 'connected' deadline 10 s counted from setRemoteDescription(answer); on connectionState 'disconnected' wait 5 s before a new offer, on 'failed' re-offer at once; backoff 1, 2, 4, 8, 8 … s without limit while the page is visible and she has not pressed stop.
