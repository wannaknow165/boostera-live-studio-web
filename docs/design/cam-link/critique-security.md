# CRITIQUE: security

## VERDICT
NOT SAFE AS DESIGNED: 2 blockers, 5 high, 7 medium, 4 low. Keep the transport (peer-to-peer WebRTC is DTLS-SRTP end to end, no media server, gateway bound to 127.0.0.1 as a relay) and replace the authorization model.

Blockers: (1) the ticket key is derived from the stage token, a URL-borne read capability that equals a database column and has already been printed once in the Lovable chat, so a wall link is enough to go live as the creator; (2) a ticket becomes a full gateway session, because the fallback uses /api/workspace/*, which controls the RTMP target, an 'rtmp' broadcast mode, paid generation and effects.

High: a 12-hour replayable ticket plus one session per handle lets a copied ticket take over a running LIVE; one CORS allow-list over /api/live/* combined with ambient loopback identity lets an allowed-origin page on the server PC act as the program page and receive her camera; 'most recent poller wins' flip-flops with two program pages and can be taken by any loopback caller; the HLS fallback airs the newest preview of any device; and the origin that will hold the raw camera, the stage link and the program role (:8800) is writable today by any web page opened on the PC (cross-site POST to /save, then innerHTML of effects/index.json inside the program page) and by the LAN when no studio key is set.

None of the fixes is large: 18 controls (must_add_for_v1), mostly in one new lib/live-link.mjs plus four small diffs on the studio server. With them v1 is acceptable on the USB bed. Public exposure additionally needs a fixed HTTPS hostname and the reverse-proxy self-check (issues 12 and 13).

Attacker summary from the code: a leaked stage link is full impersonation under v0 and nothing new after the fixes. An internet caller with the tunnel address and no credential gets static files and 401s (keep it so: authenticate before reading bodies, rate-limit). The LAN cannot reach :8801 (observed listening on 127.0.0.1) but reaches :8800 (observed listening on ::). A web page in a browser on the server PC, or any page or app on the adb-reversed test phone, is 'local' to both servers today. A paired phone is trusted but must not be able to put itself on air.

CAN WAIT: all TURN; ES256 tickets or one-time-code redemption with the existing service key; ticket refresh by postMessage; CSP sandbox on proxied media (issue 15); owner test and shorter retention on the legacy HLS routes (issue 14); vendoring hls.js; receiver-side size and bitrate caps (issue 17); an operator kill switch and an audit ring; the iframe sandbox attribute; the Vardyverse service worker / installable PWA.

## ISSUES
### 1. [blocker] Ticket key = SHA-256(stage token): a wall link (or a database read) is enough to go live as the creator
**Problem:** The stage token is a URL-borne, long-lived READ capability for the wall, not a secret. v0 makes its SHA-256 the HMAC key, so: (a) anyone who ever sees a stage link computes the key offline and mints unlimited tickets (any nonce, exp up to 12 h, renewable forever) until the wall link is rotated, which nothing prompts and which kills the wall; (b) the stored column stage_tokens.token_hash IS the signing key, so a read-only database leak, a backup or a dashboard user can mint tickets (a stored hash is normally useless to an attacker; here it is password-equivalent); (c) one value does two jobs, with coupled rotation and no domain separation; (d) the promised benefit ('no new secret copied by hand') does not exist: the gateway process never sees the stage link (it is a query parameter of the Chrome program page on :8800) and no VARDY_STAGE_TOKEN exists, so a value must be hand-copied anyway and re-copied after every rotation (the token cannot be read back; a gateway restart signs out every phone); (e) it fails open: an empty env gives key = SHA-256('') = e3b0c442...7852b855, a public constant; (f) raw 32 bytes versus 64 hex characters is unspecified. As cryptography, HMAC-SHA256 keyed with the hash of a 192-bit random token is sound; the key management is not. Impact with a forged ticket: the attacker is 'the same session' as the creator (issue 3), replaces her link, and the attacker's camera and microphone are composited and aired on her TikTok LIVE; plus everything in issue 2, the server's real IP addresses from the SDP answer, and live status.

**Evidence:** VV src/lib/stage/state.server.ts L8 `export const hashStageToken = (t: string) => createHash("sha256").update(t).digest("hex");`; L13 `|| token.length < 32) return null;`; L15 `.eq("creator", creator).eq("token_hash", hashStageToken(token))`; L21-23 rotation overwrites the single row. The token travels in a query string every 2 s: VV src/routes/stage.tsx L33 fetches `/api/public/stage/state?creator=${encodeURIComponent(creator)}&t=${encodeURIComponent(t)}`; L34 `if (r.status === 401) { setDenied(true); return; }` (after a rotation the wall stays dead until reload). The token is in the captured program window: SRV:200 `res.writeHead(302, { Location: '/fx/?clean=1' + (url.search ? '&' + url.search.slice(1) : '') })`; FXI:104 `log('קיר מהענן מאחורי המצלמה: ' + stageUrl)` (FXI:86: log = page text + console.log); FXI:110 `window.fxStage = { url: stageUrl, frame: f, gate, ... }`; APP/public/links.html:71 `'/clean/program?src=phone&stage=https://vardy-verse-connect.lovable.app/stage?creator=NAME%26t=TOKEN'`. Vardyverse map: Tohar's stage link with its token was printed in the Lovable chat (agent message 19:04:07Z). Repo grep for VARDY_STAGE_TOKEN, STAGE_TOKEN, LIVE_TICKET: not found; the only VARDY_* names are at APP/lib/vardy-ingest.mjs:107 (VARDY_BASE_URL, VARDY_SERVICE_KEY, VARDY_CREATOR_HANDLE); GW contains no reference to a stage. A correct signed-token template already exists: VV src/lib/tiktok/oauth.server.ts L13 `const sign = (secret: string, body: string) => createHmac("sha256", secret).update(body).digest("base64url");` and L25 `if (a.length !== b.length || !timingSafeEqual(a, b)) return null;`.

**Proposed change:** (A, v1 minimum) A dedicated secret LIVE_TICKET_KEY: 64 hex characters from crypto.randomBytes(32), stored as a Lovable secret and in the gateway's .env (the secrets file per APP/lib/env.mjs:7). The gateway accepts it only if it matches ^[0-9a-f]{64}$ (Buffer.from(bad,'hex') truncates silently); otherwise bearer auth is OFF and ticket requests get 503 {error:'LIVE_TICKETS_DISABLED'}; there is never a default or empty key. HMAC key = the 32 raw bytes; sig = HMAC-SHA256(key, ASCII 'v1.'+payloadB64url) as base64url without padding (43 characters). Delete from the design: derivation from the stage token or token_hash, and 'env VARDY_STAGE_TOKEN'. (B, if 'no new secret' is a hard requirement) do not sign at all: Vardyverse stores a random one-time code (hash, creator, exp 120 s, used_at) and the gateway redeems it server-to-server at POST /api/public/live/redeem with header X-Vardy-Service-Key, the secret that is already hand-copied for ingest and never travels in a URL (same key check and CREATOR_MISMATCH rule as /api/public/live/ingest). (C, when a second server or creator exists) ES256: private key as a Lovable secret, only LIVE_TICKET_PUBLIC_KEY on the Windows box, so one server cannot mint tickets for another. Independently: rotate Tohar's stage link before production; it is exposed.

### 2. [blocker] A ticket becomes a full gateway session: the fallback path runs through /api/workspace/*
**Problem:** v0 says a valid ticket 'creates or reuses a session' and that the fallback uses 'the existing chunk endpoints'. Those sit behind the single gate at GW:74-75, which hands whatever session object it gets to the whole workspace; the workspace only reads session.id. A remotely mintable ticket would therefore bypass the pairing ceremony (8-digit code created on the PC, 180 s, 8 tries per minute, 12 devices) and reach: change or clear the RTMP destination; start a broadcast in mode 'rtmp', where ffmpeg pushes whatever the client uploads to the stored TikTok ingest (going live on her account without LIVE Studio); queue paid AI generation; connect or disconnect TikTok events; 64 MiB uploads; screen effects and overlays on the LIVE; read customers, jobs and chat. If ticket sessions are stored in MobileSessions they also consume the 12-device cap and can lock pairing (DEVICE_LIMIT).

**Evidence:** GW:74-75 `const session=auth(req);if(!session)return send(res,401,{error:'PAIRING_REQUIRED'});` then `if(await workspace.handle(req,res,url,session))return;`. WS:135 `broadcasts.start({mode:b.mode,mime:b.mime,owner:session.id})`; BC:14 accepts `['preview','rtmp','record']`; BC:16 and BC:19: the rtmp output is `['-f','flv','-flvflags','no_duration_filesize',destination]`. WS:128-132 PUT /api/workspace/rtmp (`db.rtmp={url:destination.href,key:text(b.key,500),host:destination.hostname}`); WS:105 `if(!b.spendAccepted)throw fail('GENERATION_COST_NOT_ACCEPTED')` is the only brake on paid jobs; WS:125 tiktok/connect; WS:94 `read(req,64*1024*1024)`; GW:103-112 screen, overlay and stop proxies. SS:11 `if(this.sessions.size>=12)throw new Error('DEVICE_LIMIT')`.

**Proposed change:** New module APP/lib/live-link.mjs with its own LiveSessions store: Map sha256(sid) -> {id:'live_'+12 hex, scope:'live', handle, createdAt, expiresAt = now+12 h, fixed}; at most 8, evicting the oldest that does not hold the slot; memory only, like SS. In GW add one branch after the static block and BEFORE GW:74: `if(p.startsWith('/api/live/'))return live.handle(req,res,url,p,{local:localRequest(req,port),paired:sessions.get(cookies(req).wm_sid)});`. auth() (GW:25), sameOrigin() (GW:26) and MobileSessions stay untouched and never return a live session, so no existing route is reachable with a ticket. The fallback gets three live-scoped routes that wrap the Broadcasts instance already exported at WS:148: POST /api/live/capture/fallback/start {mime} -> `broadcasts.start({mode:'preview',mime,owner:live.id})` (mode fixed on the server; first stop any active broadcast of the same owner), POST /api/live/capture/fallback/<24 hex>/chunk (x-sequence, 8 MiB cap as WS:138), POST /api/live/capture/fallback/<24 hex>/stop. The hub records fallback={broadcastId, owner} (issue 6). Any other path presented with a live sid: 403 {error:'LIVE_SCOPE'}.

### 3. [high] 12-hour replayable bearer in a URL + one session per handle = takeover of a running LIVE
**Problem:** The payload is {h, exp <= 12 h, n}: n is never checked for reuse, there is no iat and no audience. 'A valid ticket creates or reuses a session bound to the handle' makes every holder of any valid ticket the same identity, and 'a new offer from the same session replaces the old attempt' then lets a copied ticket replace the creator's link in the middle of a broadcast. The ticket rides in #t=: a fragment is not sent to the server or in Referer (good), but it sits in the iframe's src attribute (readable by every script on the Vardyverse page, including analytics or session replay) and, in the top-level fallback, in the address bar, history (synced across devices), share sheets and screenshots. There is no clock-skew rule: a Windows clock that is minutes off either rejects fresh tickets or honours expired ones. The handle in the payload is not compared with anything, and nothing binds a ticket to this server. Implementation traps: crypto.timingSafeEqual throws on unequal lengths (becomes a 500 through GW:115), JSON parsed before the MAC is checked, an 'expired' answer given to unsigned input.

**Evidence:** Design text: 'payload {h: creator handle, exp: unix seconds (at most 12 h ahead), n: nonce}', 'creates or reuses a session bound to the handle', 'a new offer from the same session replaces the old attempt'. GW:115 `catch(e){if(!res.headersSent)send(res,e.status||500,{error:e.status?e.message:'REQUEST_FAILED'});`. Existing practice to match: SS:12-13 a 256-bit random token stored only as sha256; SS:15 format check before lookup (`/^[a-f0-9]{64}$/`); SS:11 the pairing code is single-use (`this.codes.delete(key)`); SS:4 it lives 180 s.

**Proposed change:** Ticket = single use, 2 minutes, only for the hand-over through the URL. Payload (JSON): {v:1, h:'<handle, lower case, ^[a-z0-9._]{2,24}$>', aud:'<gateway origin>', iat:<unix s>, exp:<iat+120>, jti:'<16 random bytes, base64url>'}. Gateway order: (1) header matches ^Bearer v1\.[A-Za-z0-9_-]{20,700}\.[A-Za-z0-9_-]{43}$; (2) recompute the HMAC and compare with timingSafeEqual only after checking both buffers are 32 bytes; (3) only then JSON.parse in try/catch; (4) h equals this server's creator (env VARDY_CREATOR_HANDLE, trimmed, leading @ removed, lower case; unset -> 503 LIVE_HANDLE_NOT_CONFIGURED); (5) aud equals the gateway's public origin (the value given to setPublicUrl; with no public URL: 'http://localhost:'+port or 'http://127.0.0.1:'+port); (6) iat <= now+60, exp >= now-60, exp-iat <= 300; (7) jti unseen (Map jti -> exp, pruned in the existing 15 s cleanup at GW:117, max 2000). Failures in 1-3: 401 TICKET_INVALID and nothing else; after 3: 401 TICKET_EXPIRED (with serverTime), TICKET_WRONG_SERVER, TICKET_REPLAYED. Exchange once: POST /api/live/session with the ticket -> 200 {sid, expiresAt, handle}; sid = 64 hex from crypto.randomBytes(32), stored as sha256; all later calls send `Authorization: Bearer live.<sid>`. Slot identity = the live session id, never the handle: the same sid may replace its own attempt; another sid (even for the same handle) gets 409 {error:'BUSY'} while the program reported 'connected' within the last 10 s; capture/stop and the fallback routes require owner === session, else 404 as BC:36 does. Capture page: the first statement reads location.hash, then history.replaceState(null,'',location.pathname+location.search) before any await or getUserMedia; the sid lives in a module variable plus sessionStorage and is never logged. On 401 the page posts {type:'live:auth-expired'} to window.parent (no secret in the message) and Vardyverse issues a new ticket and reloads the iframe. Vardyverse issues the ticket when the screen mounts (the exchange happens at page load, so 120 s is ample) and a fresh one on click for the top-level fallback link.

### 4. [high] One CORS allow-list over /api/live/* + ambient loopback identity: an allowed-origin page on the server PC is 'the computer' and can take her camera
**Problem:** The gateway's local identity is ambient (network position), not a cookie, so 'no credentials' CORS does not remove it. v0 puts one allow-list (the two :8800 origins plus the Vardyverse origin) on the whole /api/live/* prefix, and those origins must be exempted from sameOrigin() for it to work. A script on the Vardyverse origin running in any browser on the Windows server (the operator signs in there, and Vardyverse /stage runs permanently inside the program window as the wall iframe) then passes both the loopback test and CORS on the program endpoints: it polls, reads the creator's offer, answers it, and her camera and microphone terminate in that script. Separately, GET is never origin-checked today and v0's poll is a GET that consumes an offer and claims the program role, so even an <img> request from any page on the PC can steal the role or eat offers. Chrome's Local Network Access (142+) only puts a permission prompt on public-to-loopback fetches and iframes, does not cover local-to-loopback or WebRTC, and does not exist in other browsers; it must not be the control. DNS rebinding itself is already defeated on the gateway by the Host test in localRequest; keep that test exactly as it is.

**Evidence:** GW:11 localRequest = loopback peer + no cf-connecting-ip / x-forwarded-for + Host in ['127.0.0.1:'+port,'localhost:'+port]; no Origin test. GW:25 `function auth(req){return localRequest(req,port)?localSession:sessions.get(cookies(req).wm_sid);}`. GW:43 only `['POST','PUT','DELETE']` reach sameOrigin(); GW:44 `if(req.method==='OPTIONS'){res.writeHead(405);return res.end();}`. FXI:101-109 the wall iframe: `f.setAttribute('allow', 'autoplay; fullscreen'); ... f.src = stageUrl; stageEl.prepend(f);`. Tests that pin today's behaviour: APP/test/mobile.test.mjs:20-25 (rebinding and forwarded requests are not local), :61 (a foreign Origin POST gets 403), :74 `assert.equal(echoed.headers['access-control-allow-origin'],undefined)`. OLD/mobile-gateway.mjs:42 reflects the header for EVERY GET path: `if(o&&req.method==='GET'&&/^http:\/\/(localhost|127\.0\.0\.1):8800$/.test(o)){res.setHeader('Access-Control-Allow-Origin',o);res.setHeader('Vary','Origin');}` (that would also expose /api/workspace/overview, /api/mobile/frame, /api/mobile/audio-test and /api/mobile/public-url to any script on the :8800 origin). Local Network Access scope: https://developer.chrome.com/blog/local-network-access (fetch, subresources and subframe navigation from public sites; WebRTC and local-server-to-localhost are not covered).

**Proposed change:** Remove LIVE_ALLOWED_ORIGINS from CORS completely. The capture page is served by the gateway, so inside the Vardyverse iframe its fetches are same-origin (Origin host equals Host, Sec-Fetch-Site: same-origin): they pass GW:43 unchanged and need no preflight. LIVE_ALLOWED_ORIGINS is used for frame-ancestors only (issue 11). CORS exists only on /api/live/program/* and only for 'http://127.0.0.1:'+upstreamPort and 'http://localhost:'+upstreamPort (string equality, derived from upstreamPort, not a literal 8800). Handle /api/live/program/* entirely in a branch placed above GW:43 (preflight and real requests), because sameOrigin() would reject the :8800 Origin. On those paths every method including GET requires that Origin (missing or different -> 403 PROGRAM_ORIGIN_REQUIRED) AND localRequest(req,port). Headers on success, error and preflight: Access-Control-Allow-Origin: <that origin>, Vary: Origin, Access-Control-Allow-Methods: GET, POST, Access-Control-Allow-Headers: Content-Type, X-Live-Program-Key, Access-Control-Max-Age: 600; never Allow-Credentials. Every other OPTIONS stays 405. /api/live/session, /api/live/capture/*, /api/live/status and /api/live/config send no CORS header at all and reject a foreign Origin as today. Do not port the OLD GET hunk globally: scope it to /api/live/program/* plus GET /api/workspace/broadcast/<id>/files/* for the one id registered in the hub (issue 6).

### 5. [high] Program role: 'most recent poller wins' flip-flops with two pages and can be taken by any loopback caller; use a lease and a program key
**Problem:** (a) Two program pages (the Chrome --app window plus a LIVE Studio browser source of the same link, which the docs describe, or a forgotten tab) both long-poll: each new poll becomes 'most recent', the other is released and polls again, so the role flips every cycle, offers land on a random page and the picture never settles. (b) Anything that can send one loopback request with the right Host takes the role. Loopback is wider than 'our Chrome': adb reverse tcp:8801 and tcp:8800 makes every page and app on the test phone a loopback caller (a non-browser client can forge Origin), and a same-host reverse proxy with default settings makes the whole internet loopback (issue 13). (c) answer and state are not bound to the page that received the offer. (d) attemptId strength and ownership are unspecified, so one caller could answer or stop another's attempt.

**Evidence:** Design: 'One slot: one program page (the most recent poller wins)', 'GET /api/live/program/poll?program=<pageId>&after=<n>'. APP/STUDIO-CONNECT.md:18 and :24 present the program link as a Studio browser source ('מקור דפדפן'): `http://localhost:8800/clean/program?src=phone&streamer=<שם>`. GW:11 defines what 'local' means. Test-bed statement: 'adb reverse tcp:8801 and tcp:8800'.

**Proposed change:** Lease by pageId: the first poll with program=<uuid> takes the role and keeps it while that page polls at least every 40 s. Another pageId gets 409 {error:'PROGRAM_BUSY'} (it retries every 5 s and logs once) unless it sends takeover=1, which only the launcher link carries; the displaced page then gets 410 {error:'PROGRAM_REPLACED'} and stops polling for good. The poll is non-destructive: the pending offer is returned to the lease holder on every poll until POST /api/live/program/answer {program, attemptId, sdp} arrives or the attempt expires (10 s). answer and state are accepted only from the lease holder and only for the current attemptId (crypto.randomBytes(16) hex); an identical repeat -> 200 {repeated:true}, a different second answer -> 409. Program key: the gateway takes LIVE_PROGRAM_KEY from .env or, if absent, creates 24 random bytes at start and writes APP/runtime/live-program.key (git already ignores runtime/ and *.key); the launcher reads it and appends #pk=<key> to the --app link (a fragment survives the 302 at SRV:200); the page reads it, strips it with history.replaceState and sends header X-Live-Program-Key on poll, answer and state; the gateway compares with timingSafeEqual; missing or wrong -> 403 PROGRAM_KEY_REQUIRED. The key is never returned by any HTTP route.

### 6. [high] HLS fallback airs 'the newest running preview of any device': it bypasses the slot, and two stale streams block the creator
**Problem:** v0 reuses the old useServer logic: the program page scans /api/workspace/overview and plays the newest running preview broadcast, whoever owns it. Any paired device (up to 12, sessions last 12 h) or local page can therefore put its own video on air whenever WebRTC is not connected, with no BUSY rule and no ticket; an old paired test phone left on 'send video to server' goes on air the moment her link drops. In the other direction the cap is global: two stale broadcasts (starting, running and stopping all count; an abandoned one lives 60 s; no client stops on pagehide) give the creator BROADCAST_LIMIT exactly when she needs the fallback, and her own 1-2-4-8 s reconnect loop can cause it by starting a new preview on each attempt.

**Evidence:** OLD/fx/index.html:132 `const s = (d.broadcasts || []).filter(b => b.mode === 'preview' && b.state === 'running').sort((a, b) => b.startedAt - a.startedAt)[0];`. WS:81 `broadcasts:broadcasts.list()` (every owner, no owner field). BC:15 `if([...this.items.values()].filter(s=>active(s)||s.state==='stopping').length>=2)throw Object.assign(Error('BROADCAST_LIMIT'),{status:409});`. BC:9 `Date.now()-s.lastChunkAt>60000` before INPUT_TIMEOUT.

**Proposed change:** With src=live the program page never reads /api/workspace/overview. The poll answer carries the source chosen by the hub: {type:'offer', attemptId, sdp, client, iceServers} or {type:'hls', broadcastId, playback} or {type:'idle'} or 204. 'hls' is sent only for the broadcast registered through /api/live/capture/fallback/start by the session that owns the slot, and only while its state is 'running'. One fallback broadcast per owner: start stops that owner's previous one. The capture page stops it on pagehide with fetch(url,{method:'POST',keepalive:true,headers:{Authorization:'Bearer live.'+sid}}) (sendBeacon cannot carry the header), and the hub stops it once WebRTC has been 'connected' for 5 s. When the owner's link and fallback have both been gone for 10 s the hub sends {type:'idle'} and the page sets video.srcObject = null and clears the canvas, so no stranger's or frozen frame stays over the wall.

### 10. [medium] No bounds on the hub: body size, offer rate, waiters, attempts, failed credentials
**Problem:** The gateway has no global or per-IP limiter and its JSON reader stops at 4096 bytes, so the live routes will get a new reader and new long-lived requests (8 s per offer, 25 s per poll) with whatever limits the implementer picks. Unbounded, an authenticated client can park requests, replace attempts in a loop, or push multi-megabyte SDP into the program page; an unauthenticated one can make the gateway read bodies before it is rejected.

**Evidence:** GW:13 `async function body(req,max=4096)`; GW:14 jsonBody requires application/json. Gateway map section 8: no global or per-IP request limiter and no cap on concurrent long responses. Existing patterns to reuse: SS:7-8 (8 failures per IP per 60 s -> TOO_MANY_ATTEMPTS), GW:85 (429 FRAME_RATE_LIMIT), BC:41 (429 BACKPRESSURE), BC:42 (413 INVALID_CHUNK_SIZE).

**Proposed change:** Authenticate before reading any body (as the pipeline does at GW:74). Own reader: Content-Type application/json required (415 JSON_REQUIRED), cap 65536 bytes (413 BODY_TOO_LARGE). sdp: a string of 200 to 60000 characters starting with 'v=0', at most 3 'm=' lines and 40 'a=candidate:' lines, else 400 INVALID_SDP; facing in ['user','environment']; w and h integers 160 to 1920. One offer in flight per session (a second -> 429 OFFER_IN_FLIGHT); at most 10 offers per minute per session (429 OFFER_RATE_LIMIT); one pending attempt in the hub, expiring after 10 s; no parking when the program is offline (503 PROGRAM_OFFLINE at once, after auth). Failed tickets or sids: 8 per IP (cf-connecting-ip, else the socket address) per 60 s -> 429 TOO_MANY_ATTEMPTS. At most 8 live sessions and 2000 jti entries. One poll waiter (an older waiter of the same lease is answered 204). hub.close() answers every waiter and clears every timer so server.close() does not hang; timers are unref'd as at GW:117. Never write SDP, tickets, sids or keys to the console or to the page log (FXI:86 keeps an unbounded log string).
