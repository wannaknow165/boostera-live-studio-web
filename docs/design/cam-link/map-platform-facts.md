(1) HTTPS public page -> http://localhost:8801 / 127.0.0.1 / LAN IP (Chrome)
Short answer: Not mixed content for loopback, but since Chrome 142 it needs a user permission (Local Network Access, LNA). Private Network Access preflight headers are no longer needed.
- Mixed content: loopback URLs (http://127.0.0.1, http://localhost) count as secure origins, so fetch or iframe from HTTPS is not blocked as mixed content. A private IP such as http://192.168.x.y IS mixed content unless LNA exempts it.
- LNA shipped in Chrome 142 on desktop and Android (chromestatus shipping stage: desktop 142, android 142; I found no Android-specific release note). It gates public -> local/loopback requests for fetch(), subresources and subframe navigations, so an iframe of http://localhost:8801 inside a public HTTPS page also prompts. WebSockets and WebTransport were added in Chrome 147.
- Chrome 145 split the permission: `loopback-network` (127.0.0.0/8, ::1, localhost) and `local-network` (RFC1918, link-local, ULA, .local). `local-network-access` stays as a legacy alias.
- Mixed-content exemption once permission is granted: target is a private IP literal, a .local name, or fetch(url, {targetAddressSpace: 'local' | 'loopback'}). ws:// to IP literal/localhost/.local is exempt from 147; `targetAddressSpace` for WebSocket is listed for Chrome 154.
- Only secure contexts can get the permission; it is auto-denied for insecure top-level pages (reverse origin trial extended to M152).
- Iframes: Permissions-Policy features `local-network` and `loopback-network` default to 'self'. A cross-origin iframe needs allow="local-network; loopback-network" (legacy allow="local-network-access" is an alias).
- NOT LNA: loopback -> anything and local -> local. So the program page http://localhost:8800 calling http://localhost:8801 never prompts; it only needs ordinary CORS.
- Headers: PNA preflights (Access-Control-Allow-Private-Network) were never enforced as blocking and are deprecated; harmless to keep. Normal CORS still applies. Code today: server.mjs:192 sends `'Access-Control-Allow-Origin': '*', 'Access-Control-Allow-Headers': '*', 'Access-Control-Allow-Methods': 'GET,POST,PUT,DELETE'`, which is sufficient.
- WebRTC is NOT gated yet: chromestatus "Local Network Access Restrictions for WebRTC" is Proposed with no milestone, and Chromium main defines kLocalNetworkAccessChecksWebRTC as DISABLED_BY_DEFAULT (kLocalNetworkAccessChecks, ...WebSockets and ...WebTransport are enabled). A Jamf support article claiming Chrome 146 covers WebRTC contradicts the source.
- For our own Windows box: policies LocalNetworkAccessAllowedForUrls / LocalNetworkAccessBlockedForUrls; Chrome 146 added LocalNetworkAccessIpAddressSpaceOverrides and LocalNetworkAccessPermissionsPolicyDefaultEnabled; testing switch --ip-address-space-overrides=127.0.0.1:8801=public.
- Safari/iOS has no LNA. HTTPS -> http://LAN-IP is plain mixed content and blocked. WebKit also does not follow the spec for loopback (bug 171934 still open; Safari 18 regression bug 279249 was only narrowly fixed in March 2025).

(2) getUserMedia inside a cross-origin iframe
Short answer: Works on Chrome Android and iOS Safari with allow="camera; microphone", provided every ancestor is a secure context. No Permissions-Policy response header is required.
- Chrome: the allow attribute has been required since M64 (January 2018). Since M71 (Permission Delegation, includes Android, excludes WebView) the user decides only about the TOP-LEVEL site and the top-level page delegates to the frame.
- Safari: allow="camera; microphone" landed in WebKit r225963 (2017-12-14, bug 167430); caniuse shows the iframe allow attribute from Safari 11.1 / iOS 11.3. Which origin the Safari prompt names: UNVERIFIED.
- Secure context: in insecure contexts navigator.mediaDevices is undefined. A framed http://LAN-IP document is not a secure context, so allow cannot help.
- Permissions-Policy header: camera/microphone default to 'self', and the allow attribute does the cross-origin delegation. If the TOP-LEVEL document sends a header naming camera/microphone, its allowlist must include the iframe origin (Chromium). A header on the framed document can only restrict itself. Safari does not implement the Permissions-Policy response header (caniuse: unsupported through 27.x).
- iOS Home Screen (standalone) problems:
  - Permission is not persisted: re-prompt on every cold launch (bug 215884, reports through 2026; follow-up bug 327237 filed 2026-10-12).
  - Hash/pushState navigation in standalone stopped capture and reset permission (bug 215884; iOS 17.4 pushState regression, bug 272704, fixed).
  - Camera freeze in installed PWA on iOS 17.5.1 (bug 275527).
  - Wake Lock was broken in Home Screen apps until 18.4.
  - Since Safari 26.0 any site added to the Home Screen becomes a web app, so standalone is now the common case.
- WebKit lets only one page capture at a time; a second getUserMedia can mute the first stream.

(3) iOS Safari as a WebRTC sender
- Codecs: H.264 (Constrained Baseline) is hardware encoded/decoded on iOS. VP8 since Safari 12.1 is software only, with more CPU and battery cost (MDN). VP9: WebKit bug threads from 2021 say iOS 15 can send/receive it with a software encoder (secondary). AV1: tied to devices with hardware AV1 decode (Safari 17 note; bug 311593 from 2026 mentions a WebRTC AV1 feature flag); AV1 encode UNVERIFIED. HEVC: exists in WebKit WebRTC (Safari 16.4 note mentions the WebRTC HEVC encoder); Chrome receives H.265 from 136 with hardware support. Use H.264 and confirm with RTCRtpSender.getCapabilities('video') on the device.
- Resolution/fps: no current documented hard cap found (the 720p cap reports are from iOS 11). Code asks portrait: public/mobile/app.js:76 `getUserMedia({video:{facingMode:{ideal:facing},width:{ideal:720},height:{ideal:1280},frameRate:{ideal:targetFps,max:targetFps}},audio:false})`.
- Portrait pitfall: WebKit bug 323550 (NEW, filed 2026-09-06; iOS 26.6 and 27.0). Front camera getSettings() first reports the requested portrait size, then flips to landscape after the first frame (about 0.4 s). MediaRecorder MP4 then plays sideways when portrait dimensions are requested, while a landscape request yields an upright portrait file. Read dimensions only after the first frame. How rotation reaches a WebRTC receiver on iOS 27: UNVERIFIED.
- Background/lock: capture is interrupted and tracks fire mute (sometimes ended). Reports: audio track ended after more than 30 s in background (bug 204681); camera left muted after returning (bugs 230698, 232599). Recovery pattern: on visibilitychange check track.muted/readyState, call getUserMedia again, then sender.replaceTrack. Screen-lock behaviour on iOS 27: no primary source.
- Non-trickle ICE (waiting for iceGatheringState 'complete'):
  - WebKit exposes host candidates only after capture permission, so create the offer after getUserMedia resolves.
  - 'complete' can be late or never arrive: bug 182906 (2018, never completes without srflx); bug 312332 (Safari 26.3-26.4 with relay policy: stuck in gathering, zero candidates; fixed in main 2026-04-17, shipping version not stated); Apple forum thread 803537 (gathering sometimes does not start).
  - Unreachable STUN/TURN URLs stretch gathering. Always add a 1-2 s watchdog or use trickle.
- Screen Wake Lock: supported from Safari/iOS 16.4 (2023-03-27); Safari 17 fixed a permission-denied-after-visibilitychange bug; Home Screen web apps fixed in 18.4 (2025-03-31). In iframes it is policy-controlled (`screen-wake-lock`, default 'self'), so a cross-origin frame needs allow="screen-wake-lock" (Chromium 88+). Whether WebKit honors that token: UNVERIFIED; request from the top-level document. Code already does this: app.js:83 `if(navigator.wakeLock)try{wakeLock=await navigator.wakeLock.request('screen');}catch{}` and re-acquires at app.js:189.

(4) iOS Safari MediaRecorder
- Availability: enabled by default from the iOS 14.3 beta (WebKit blog, 2020-11-23); caniuse lists Safari 14.1 / iOS 14.5. Originally MP4 with H.264 + AAC only.
- Safari 18.4 (2025-03-31) added WebM (VP8/VP9 + Opus per bug reports) and rewrote the recorder; HEVC is also recordable; a requested avc1 type is reported back as `video/mp4; codecs=avc1.42000a`. Safari 26.0 added ALAC and PCM audio.
- Fragmented MP4: yes. WebKit's MediaRecorderPrivateWriterAVFObjC.mm uses AVAssetWriter in segmented mode (AVFileTypeMPEG4, AppleHLS profile for audio+video, CMAF otherwise) and calls flushSegment per chunk. So chunk 1 carries the init segment (ftyp+moov) and later chunks are moof+mdat fragments that are not independently playable. Concatenated in order they form a streamable fMP4, which is why `-i pipe:0` works. That FFmpeg accepts it in every case is my inference, not a documented guarantee.
- Bugs: 18.4 betas corrupted MP4 under repeated requestData (bug 290002, fixed in beta 4). WebM VP8/VP9 recordings came out rotated 90 degrees on iOS 18.4 because WebM has no rotation metadata (bug 290223; fix landed 2025-04-29 and missed 18.5). Portrait MP4 bug 323550 is described in (3).
- Code impact: public/mobile/render.js:76 prefers WebM: `types=['video/webm;codecs=vp8,opus','video/webm','video/mp4;codecs=avc1.42E01E,mp4a.40.2','video/mp4']`. On iOS 18.4+ this now selects software VP8 WebM instead of hardware H.264 fMP4. app.js:18 has the opposite (MP4-first) order.
- Current path latency is structural: render.js:79 `broadcastRecorder.start(1000)`; lib/mobile-broadcast.mjs:18 `'-analyzeduration','1000000','-probesize','1000000','-i','pipe:0'` with libx264 re-encode; :19 `'-f','hls','-hls_time','2','-hls_list_size','6'`. The recorded stream is a canvas capture (app.js:155 `output.captureStream(targetFps)`), so it stalls when the page is backgrounded.

(5) Chrome ICE candidates and mDNS
- When: host candidate IPs are replaced by generated .local names while the origin has neither microphone nor camera permission. Feature WebRtcHideLocalIpsWithMdns is ENABLED_BY_DEFAULT, with no platform conditional, in Chromium main.
- Lifted with permission: yes. FilteringNetworkManager checks mic and camera permission; if either is granted, enumeration is allowed and the mDNS responder is dropped, so real IPs on all interfaces are exposed. Before that only the default local addresses are used.
- Android: the responder is compiled only under ENABLE_MDNS, and net/features.gni sets enable_mdns = is_win || is_linux || is_chromeos || is_fuchsia || is_apple || enable_desktop_android_extensions. So ordinary Chrome for Android does not generate mDNS candidates. Whether it resolves remote .local candidates: UNVERIFIED, treat as unreliable.
- --disable-features=WebRtcHideLocalIpsWithMdns is still valid and is not in the bad-flags infobar list. Policy alternative: WebRtcLocalIpsAllowedUrls (chrome.* 79+, chrome_os 79+; not Android).
- WebRtcUdpPortRange is still available and not deprecated (chrome.* 54+, chrome_os 54+, android 54+; example value 10000-11999; needs restart).
- Practical consequence: a receive-only Chrome on Windows advertises only .local host candidates. The phone has camera permission and advertises real IPs, so ICE can still complete from Windows towards the phone (peer-reflexive). Exposing real IPs on the Windows side by policy or flag removes the dependency.

(6) Autoplay and covered windows (Chrome on Windows)
- Receive-only page: unmuted playback IS blocked without a gesture. AutoplayPolicy::IsDocumentAllowedToPlay allows only: force-allow flag, document currently capturing user media, user-exception flag (site setting/policy), sticky user activation, or high Media Engagement on the outermost main frame. There is no exemption for a remote MediaStream. Muted autoplay works; AudioContext starts suspended.
- --autoplay-policy=no-user-gesture-required is valid (media_switches.cc; values document-user-activation-required, no-user-gesture-required, user-gesture-required; the command line wins). Policy alternatives: AutoplayAllowed, AutoplayAllowlist. Cross-origin iframes need allow="autoplay".
- --disable-backgrounding-occluded-windows, --disable-renderer-backgrounding and --disable-background-timer-throttling all still exist in content_switches.cc.
- Infobar: bad_flags_prompt.cc does not list those switches, --autoplay-policy, --disable-features or --ip-address-space-overrides. It DOES list --use-fake-ui-for-media-stream, --unsafely-treat-insecure-origin-as-secure, --disable-web-security and --ignore-certificate-errors; those would put a warning bar inside the captured window.
- Covered window: Windows native occlusion tracking is on by default (feature CalculateNativeWinOcclusion; policy WindowOcclusionEnabled, chrome.win 90+). For an occluded window, in the Chromium doc's words, "rendering stops, and js is throttled", and its foreground tab is treated like a background tab. Minimized windows are hidden. Windows on another virtual desktop, and all windows while the screen is locked, count as occluded. Transparent, cloaked, floating and non-rectangular windows do not occlude.
- Background timers run about once per second; the once-per-minute tier does not apply while an RTCPeerConnection has a live track or audio played in the last 30 s.
- So if LIVE Studio fully covers the Chrome program window, the captured picture freezes unless occlusion is disabled (the switch, --disable-features=CalculateNativeWinOcclusion, or the policy set to false). Never minimize.

(7) Low-latency receiving in Chrome
- RTCRtpReceiver.jitterBufferTarget: milliseconds; negative or above 4000 throws RangeError; it is a hint, the UA still adapts. Support: Chrome 124 (the intent listed 123), Firefox 115, Safari/iOS 27; MDN marks it Baseline since September 2026.
- playoutDelayHint: the older Chromium-only attribute, in SECONDS; jitterBufferTarget is essentially its rename.
- Sensible value on a LAN: 0 on both audio and video receivers (they are synced, so set both); raise to 30-60 ms if playback stutters. Fallback: receiver.playoutDelayHint = 0.
- The sender-side playout-delay RTP header extension (min/max in 10 ms units) can force minimal delay, but only a native or SFU sender can set it, not a phone browser.
- Other levers: direct host-to-host UDP (no TURN, no TCP); H.264 with hardware encode on the phone and hardware decode on Windows; sender degradationPreference 'maintain-framerate' and a bitrate cap; draw from requestVideoFrameCallback (at most one vsync late); measure with rVFC metadata (captureTime, receiveTime, processingDuration) and getStats jitterBufferDelay.

(9) TURN
- coturn use-auth-secret (TURN REST API): username = "<timestamp>:<userid>" (separator ':' by default, changeable with --rest-api-separator); password = base64( HMAC-SHA1( key = shared secret, message = that username ) ). The timestamp is the EXPIRY time in UNIX seconds (draft-uberti; recommended ttl 86400). The secret comes from static-auth-secret or the turn_secret DB table. A realm must be set; static -u users cannot be combined with it.
  Node: username = `${Math.floor(Date.now()/1000)+ttl}:${userId}`; credential = crypto.createHmac('sha1', secret).update(username).digest('base64').
- Cloudflare Realtime TURN pricing: $0.05 per GB, with a 1,000 GB free tier (Cloudflare's pricing table says per month and shared with SFU; the FAQ just says 1,000 GB). Billed only on data sent from Cloudflare to the TURN client; free when used with the Realtime SFU; STUN at stun.cloudflare.com:3478 is free and unlimited.
- Cloudflare credentials: create a TURN key (dashboard or API), then server-side POST https://rtc.live.cloudflare.com/v1/turn/keys/<KEY_ID>/credentials/generate-ice-servers with Authorization: Bearer <key API token> and body {"ttl": 86400}. It returns 201 with an iceServers array (urls, username, credential). Expiry is at most 48 hours; a revoke endpoint exists.
- Cloudflare limits: no TCP relay (RFC 6062); IPv4 relay addresses only; permissions towards private IP ranges are refused. The returned list may include port-53 URLs that browsers block, so filter them when not trickling.
- Minimal iceServers: [{urls:'stun:stun.cloudflare.com:3478'}, {urls:['turn:turn.cloudflare.com:3478?transport=udp','turn:turn.cloudflare.com:3478?transport=tcp','turns:turn.cloudflare.com:5349?transport=tcp'], username, credential}]. On the same LAN the TURN entry is only a fallback; keep the list short because every server lengthens non-trickle gathering.

(10) MediaPipe selfie segmentation fed by a remote WebRTC <video> (Chrome)
- No Chrome-specific bug about remote WebRTC frames or texture upload was found in the MediaPipe tracker ("not found").
- Timestamps must strictly increase; one out-of-order value can break the graph permanently (issue #5743, open). Workarounds from that thread: use performance.now() or a counter rather than frame timestamps, and recreate the ImageSegmenter on error. With WebRTC, frame/media timestamps can jump on reconnect or track replacement.
- Web tasks run synchronously; the official pattern is segmentForVideo(video, performance.now()) driven per frame.
- requestVideoFrameCallback (Chrome 83, Safari 15.4, Firefox 132) fires per presented frame and exposes WebRTC metadata (captureTime, receiveTime, rtpTimestamp, presentedFrames). It stops when the page is hidden or occluded, which ties back to (6).
- The engine already decouples MediaPipe from the source: fx/fx-engine.js:472-473 `this.segCtx.drawImage(v, 0, 0, this.segIn.width, this.segIn.height); const sr = this.seg.segmentForVideo(this.segIn, ts), m = sr.confidenceMasks?.[0];`. - A remote track's resolution can change mid-stream (sender adaptation, rotation), so guard videoWidth > 0 and handle the video 'resize' event.
- MediaPipe is loaded from a CDN at runtime: fx/opponent.js:28 `'https://cdn.jsdelivr.net/npm/@mediapipe/tasks-vision@0.10.14/vision_bundle.mjs'`.
- Known GPU-delegate issues exist on Firefox (#5879) and iOS Safari with selfie_multiclass (#6142); they matter only if segmentation moves to the phone.

## GOTCHAS
- iPhone cannot talk HTTP to the LAN gateway from the HTTPS Vardyverse page: Safari has no Local Network Access model, so fetch/WebSocket/iframe to http://<LAN-IP>:8801 is blocked as mixed content. Signaling must travel over HTTPS/WSS; only the WebRTC media can go LAN-direct.
- A page served from http://<LAN-IP>:8801 (for example the gateway's /mobile/ PWA opened by IP) is not a secure context on any phone: navigator.mediaDevices is undefined, and no iframe allow attribute fixes that.
- Chrome 142+ (desktop and Android): a public HTTPS page reaching localhost or a private IP triggers a permission prompt; since 145 loopback and LAN are separate permissions. It only bypasses mixed content for IP literals, .local names or fetch with targetAddressSpace. In a cross-origin iframe it also needs allow="local-network; loopback-network".
- The program page http://localhost:8800 calling http://localhost:8801 is loopback-to-loopback: no LNA prompt, only CORS. Access-Control-Allow-Private-Network is obsolete.
- LNA for WebRTC exists in Chromium but is disabled by default (kLocalNetworkAccessChecksWebRTC). If Google enables it, a public HTTPS page connecting to LAN host candidates will start prompting.
- public/mobile/render.js:76 lists WebM/VP8 before MP4. Since iOS 18.4 Safari supports WebM in MediaRecorder, so iPhones now pick software VP8 WebM (more heat, and a 90-degree rotation bug in 18.4/18.5) instead of hardware H.264 fMP4. app.js:18 uses the opposite order.
- WebKit bug 323550 (open, iOS 26.6 and 27.0): front camera in portrait reports the requested size, flips to landscape after the first frame, and MediaRecorder MP4 plays sideways when portrait dimensions are requested. app.js:76 requests 720x1280. Read dimensions only after the first frame.
- iOS Safari MediaRecorder chunks are fragmented MP4: only the first chunk has the init segment. A lost or reordered chunk, or starting FFmpeg mid-stream, breaks the pipe input.
- A fully covered Chrome window on Windows stops rendering (native occlusion); minimized, locked screen and other virtual desktops behave the same. The program window needs occlusion disabled and must never be minimized.
- Chrome switches apply only when a new browser process starts; if Chrome is already running on that profile they are ignored. Use a dedicated --user-data-dir for the program window (general Chrome behaviour, not re-verified in this run).
- --use-fake-ui-for-media-stream, --unsafely-treat-insecure-origin-as-secure, --disable-web-security and --ignore-certificate-errors show a warning infobar that would appear in the captured window. --autoplay-policy, --disable-features and the backgrounding switches do not.
- A receive-only Chrome page gets no autoplay exemption: remote WebRTC audio stays silent until a click, unless the autoplay switch or the AutoplayAllowlist policy is used. Media Engagement can make it work by accident on a dev machine and fail on a fresh profile.
- The receive-only Chrome on Windows advertises only mDNS .local host candidates. Chrome for Android has no mDNS stack compiled in, so LAN connectivity relies on the phone exposing real IPs (it does once camera permission is granted). Create the phone's offer after getUserMedia resolves.
- Do not wait unconditionally for iceGatheringState 'complete' on Safari: there are historical and 2026 bugs where it is late or never fires, and unreachable STUN/TURN URLs (including Cloudflare port-53 entries) stretch gathering. Use a watchdog.
- Installed iOS web apps re-prompt for camera/microphone on every cold launch, and navigation inside the app has repeatedly killed capture in past iOS versions. Since iOS 26, Add to Home Screen makes any site a web app by default.
- Safari ignores the Permissions-Policy response header and honors only the iframe allow attribute. In Chrome, a top-level header that names camera/microphone without the iframe's origin silently blocks delegation.
- jitterBufferTarget is in milliseconds, playoutDelayHint is in seconds. Safari has jitterBufferTarget only from version 27; the Windows Chrome receiver has both.
- setCodecPreferences expresses what a peer wants to receive. To make the phone send H.264, set it on the phone's transceiver before the offer and on the Windows receiver, and sort rather than filter so RTX/FEC survive.
- Cloudflare TURN refuses permissions to private IP ranges, has no TCP relay and caps credentials at 48 hours. It is a fallback for off-LAN use, not a way to reach a LAN address.
- MediaPipe video mode never recovers from a non-increasing timestamp; do not feed it WebRTC frame timestamps. tasks-vision is loaded from jsdelivr at runtime, so the broadcast machine depends on that CDN.
