## GOTCHAS
- The gateway rejects what the new routes need, before any routing: APP/mobile-gateway.mjs:43 answers 403 ORIGIN_REJECTED to every POST/PUT/DELETE whose Origin host differs from the Host header (or whose sec-fetch-site is cross-site), and L44 answers 405 to every OPTIONS. CORS handling for the live-link routes has to sit above both lines and apply to those routes only.
- jsonBody() reads at most 4096 bytes (mobile-gateway.mjs:13-14, body(req,max=4096)) and takes no size argument. A real browser SDP offer with audio and video is usually larger, so the new routes would answer 413 BODY_TOO_LARGE unless they read the body with their own cap.
- Route placement matters: L74 answers 401 PAIRING_REQUIRED to anything without a pairing cookie that is not loopback, and L75 hands every /api/workspace/* path to the workspace, which answers 404 WORKSPACE_ROUTE_NOT_FOUND (lib/mobile-workspace.mjs:144). Ticket-authenticated routes must come before L74 and must not live under /api/workspace/.
- A new PWA file is not served until it is added to the name whitelist at mobile-gateway.mjs:67 (otherwise 404 NOT_FOUND). It should also go into SHELL in public/mobile/sw.js:1 with a bumped CACHE name ('wanna-fx-mobile-v5' today), or installed phones keep the old shell.
- The /mobile/ pages carry a CSP (mobile-gateway.mjs:71): script-src 'self' plus jsdelivr, so no inline script and no script from the :8800 origin; connect-src 'self' plus two CDNs, so the phone page can fetch only its own origin. Signaling from the PWA must go through the gateway origin.
- Local versus remote is decided by headers, not by the socket: localRequest() (mobile-gateway.mjs:11) needs a loopback address AND no cf-connecting-ip AND no x-forwarded-for AND Host equal to 127.0.0.1:<port> or localhost:<port>. The gateway binds 127.0.0.1 only, so tunnel traffic also arrives from loopback. In tests every plain request is the 'local-desktop' session; a phone is simulated with {host:'phone.example','cf-connecting-ip':'203.0.113.5'}.
- The port must be known before the gateway is built, because localRequest compares the Host header with the port given to createMobileGateway. That is why tests probe a free port first (mobile.test.mjs:48) instead of listening on 0.
- mobile.test.mjs builds its gateway without workspaceRoot, so it reads the real APP/data files. New HTTP tests should copy workspace.test.mjs:23 instead (temp workspaceRoot, env:{}, workspaceOptions:{tools:{ffmpeg:'not-used',installed:false}}) to stay isolated and to avoid configureMediaTools changing PATH.
- server.mjs (the studio server) cannot be imported in a test: it loads env, creates folders and calls server.listen at module top level (server.mjs:22-27, 450). Anything on the program side that needs a unit test must live in lib/ or in an fx/ module. Files under fx/ are served with no whitelist (server.mjs:289).
- npm test is an explicit file list (package.json:8); a new test file that is not added there never runs. phone-gate.test.mjs is deliberately outside it because it needs --experimental-test-module-mocks.
- Node has no RTCPeerConnection and the project has no wrtc-like package, so node tests can only exercise signaling with opaque SDP strings and fake peer classes. Real media can be proven only in the Playwright browser run.
- A browser module is importable under node only if it has no absolute imports and no DOM access at load. Existing PWA modules import '/mobile/battle.js' style paths, which node resolves against the disk root and fails.
- OLD's two unported hunks hard-code ports: useServer() builds ':8801' and the CORS line matches ':8800' literally. Both break under run-browser.mjs (18880/18881) and whenever PORT or MOBILE_PORT is changed. Derive them from upstreamPort and from a page parameter.
- In fx/index.html the source is chosen only after 'await fx.init()' (L200-205), which downloads MediaPipe from two CDNs, and any unknown ?src= value falls into useSrc() at L205 and is played as a file name. A new source value needs its own branch above L205.
- sec-fetch-site: a page on http://localhost:8800 calling http://127.0.0.1:8801 is cross-site and is refused by sameOrigin() even if its Origin were allowed; 127.0.0.1:8800 to 127.0.0.1:8801 is same-site. OLD's useServer() already mirrors the page's hostname for this reason.
- Long polls and shutdown: server.close() waits for requests in flight, so a pending poll keeps the test (and the gateway's own stop path at mobile-gateway.mjs:136, which has a 2 s hard exit) waiting unless the hub releases its waiters on close. Timers should be unref'd as elsewhere (mobile-gateway.mjs:117, vardy-ingest.mjs:137). Through the Cloudflare quick tunnel a silent request is cut at roughly 100 s, so keep the poll time well under that.
- crypto.timingSafeEqual throws when the two buffers differ in length. Unhandled, that becomes 500 REQUEST_FAILED through the catch-all at mobile-gateway.mjs:115 instead of a 401; check lengths first and test a wrong-length signature.
- The pairing cookie is 'wm_sid; HttpOnly; SameSite=Strict' (mobile-gateway.mjs:57), so it is never sent from a page on another site such as the Vardyverse origin. If the capture page is served from Vardyverse it can authenticate only with the bearer ticket, and its requests need the preflight path. The tunnel address is a random trycloudflare URL per start, written to runtime/mobile-url.txt.
- The gateway sends no CORS header today and a test asserts it (mobile.test.mjs:74). OLD's GET-only hunk still passes that test only because the test sends no Origin header; keep new CORS headers conditional on an allowed Origin.
- Line endings: core.autocrlf=true comes from the system gitconfig only and there is no .gitattributes; the working copy is CRLF and the index LF. Keep CRLF when editing existing files. mobile-gateway.mjs has no final newline, so appending one shows as a changed last line.
- .gitignore traps for fixtures: any folder named data/ or runtime/, and any *.key, .env.*, *.log or *.zip file, is ignored anywhere in the repo. A fixture at test/data/x.json or a file named turn.key would silently stay out of the commit; test/fixtures/x.json is fine.
- The repo path contains a space. new URL('../fx', import.meta.url).pathname yields '/C:/My%20Web%20Sites/…' on Windows (phone-gate.test.mjs:32 gets away with it because the path is never opened). Use fileURLToPath, or pass the URL object straight to fs as mobile.test.mjs:31 does.
- The version string '1.2.0' is written in three places (package.json:3, mobile-gateway.mjs:79, lib/mobile-workspace.mjs:47) and start-mobile.mjs:16 decides 'already running' from version.startsWith('1.').
- run-browser.mjs passes the whole parent environment to its servers and blanks only the provider keys it knows (L14). Any new secret name must be given an explicit test value there. The copy excludes .env and server.env, so file-based settings never reach the test servers.
- Browser tests are not self-contained: they need internet for MediaPipe and hls.js, and the bundled Chromium has no H.264, so a loopback call negotiates VP8/VP9 unless launched with channel='chrome'.
- The production copy is live on this machine now (8800 on all interfaces, 127.0.0.1:8801, 47831, and the LIVE Studio bridge on 9225). Unit tests use ephemeral ports and run-browser.mjs refuses to start if 18880/18881 are taken, but the ffmpeg tests do use CPU; avoid running them during a broadcast.
- MOBILE_PORT is read from process.env only (mobile-gateway.mjs:122, start-mobile.mjs:6), not from server.env, unlike PORT. The new VARDY_* names appear in neither example file; new settings should be added to .env.example (secrets) or server.env.example (plain settings).
- workspace.test.mjs:26 passes a host header through fetch; whether Node's fetch really sends a custom Host was not verified. For tests that depend on the Host header use the http.request helper from mobile.test.mjs:50-53.

## OPEN QUESTIONS
- Total runtime was not measured because running the suites would break the read-only rules (ports, ffmpeg, temp files) while the production copy is live. Estimates: npm test about 5-15 s wall (capped by a 40 s test timeout), phone-gate about 13-16 s, browser suite minutes. Should a later step with permission to run tests record the real numbers?
- Where is the phone capture page served from: the gateway PWA (/mobile/, same origin, pairing cookie) or the Vardyverse site (cross-origin through the tunnel, bearer ticket only)? This decides the CORS allow-list, whether preflight tests target the Vardyverse origin, and how the phone learns the current tunnel address.
- What signs the ticket: a shared secret (HMAC) known to the gateway, or an asymmetric key published by Vardyverse? Node here supports both (HMAC, Ed25519, ES256). The forgery and key-missing tests differ accordingly, and so does the env name to add.
- Are tickets single-use? The replay test (B6) applies only if they are.
- Long-poll only, or also WebSocket? ws 8.22.2 is already a dependency and Node 22+ has a global WebSocket client, but the gateway has no upgrade handler today and the task wording assumes long-poll.
- Trickle ICE or a single complete offer/answer? A single exchange keeps the hub and its tests simple but makes the SDP larger, which matters for the body cap.
- Which TURN service, if any? A static-secret TURN server needs only the HMAC helper (test C1); a provider with its own credential API needs an injected fetch and different tests.
- Should phone-gate.test.mjs be added to npm test now that Node 24 is the local runtime, or stay a separate command for Node 22 compatibility?
- Chromium flags for a same-machine WebRTC loopback (--allow-loopback-in-peer-connection, --disable-features=WebRtcHideLocalIpsWithMdns) and WebRTC inside the headless-shell build were not tried here; they need one real browser run to confirm.
