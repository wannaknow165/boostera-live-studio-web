# Hosted phone camera and Studio account panel

This is the existing camera page served at the customer's HTTPS camera address. It preserves the deployed AR, microphone and LiveKit camera behavior, and adds Studio account controls directly to that same page. The original frontend was recovered from the running `20261111-v2` release; runtime licensing configuration remains outside Git under `/etc/boostera-camera`.

`/mobile/box.js` is shared with the existing mobile box panel. A `#pair=` invitation is redeemed once at the existing pairing endpoint and immediately removed from the address bar. The phone receives a Secure, HttpOnly, SameSite=Strict cookie. Only hashed session tokens are saved on disk; sessions survive service restarts and retain the existing 12-hour expiry. Signing out revokes the paired phone session. It does not change the account owned by Studio.

The small `phone-control.mjs` deployment entry point reuses `MobileSessions` and `MobileStudio` without loading the media/generation workspace. It exposes only pairing, phone-session and native account/QR operations. It binds to loopback port 8801 behind the existing HTTPS proxy; the proxy replaces client address headers. Pairing invitation issuance remains loopback-only. This entry point adds no npm dependencies. It was initially exercised on the host's existing Node runtime, then moved to an isolated Node 24 runtime downloaded from the official distribution and checked against its published SHA-256. The system Node installation was preserved. HTTP/session tests and service health were verified on that isolated runtime.

`boostera-phone-control.service` is the deployed unprivileged service. Its state directory is private, source is read-only, and it is enabled at boot. The camera release is switched through `/srv/boostera-camera/current`. Earlier camera releases and Caddy configuration were backed up under `/root/boostera-backups/phone-panel-*` before publication.

On 2026-11-13 the public camera page was verified in an isolated browser using a real one-use owner invitation. The page displayed the Studio connection button, `connected to your box`, and `Studio is still preparing`. The phone remained paired after restarting the service and reloading the page. Sign-out was then verified and the test session revoked. Unauthenticated native-account access returns 401; public pairing-code issuance returns 403. This is deployed phone-panel evidence, not native TikTok login, Windows media input or battle evidence.

The native controller is still unavailable inside the hosted Windows VM. Account requests therefore return an unavailable state and the page shows preparation, without manufacturing a QR or claiming that TikTok is connected. The gateway currently expects its native controller at the fixed private loopback address. A verified private route to the Windows controller is required before native account approval can work.
